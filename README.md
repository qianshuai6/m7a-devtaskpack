## 功能简介

- **后台运行**：游戏跑在独立虚拟显示器上，你可以同时刷视频、聊天、看文档，互不打断
- **日常**：启动游戏、领取月卡、邮件、清体力、每日实训、关闭游戏
- **清体力**：拟造花萼（金/赤）、凝滞虚影、侵蚀隧洞、饰品提取、历战余响，6 种副本全覆盖
- **每日实训**：勾选式执行，不做不可靠的任务列表 OCR，可指定要做哪几项
- **忘却之庭 · 混沌回忆**：自动逐层挑战（第 7~12 层），满星层跳过，自动开自动战斗并领奖
- **兑换码**：清单从站点实时拉取，按活动分组、限时码到期自动跳过，也能自己加码
- **任务链**：卡片式任务列表，支持拖拽排序、就地调参、定时执行
- **实时预览**：App 内等比放大查看虚拟屏画面，长屏设备自动做黑边适配
- **日志与诊断**：时间线式任务日志，一键导出日志包用于排查
- **触控自愈**：注入失败自动清理残留手势并降级重试，避免「画面正常但点不动」

## 🚀 快速上手

```
① 安装 APK
② 授予 Shizuku 或 Root 权限
③ 首次启动会引导完成：
    · 用户协议确认（含风险提示）
    · 权限后端选择（Shizuku / Root）
    · 权限授予
④ 进入「首页」，在任务卡片里勾选今天要做的项目
⑤ 点「开始任务」
```

首次运行前建议：

- 关闭游戏的**省电优化**（系统设置 → 电池 → 本应用 → 不限制）
- 确保游戏已登录，并且停在大厅
- 若使用 Shizuku，保持 Shizuku 服务在运行

### 为什么需要特权服务

采集虚拟屏画面、向虚拟屏注入触摸事件，都需要 **shell / root 级权限**。本项目提供两种后端：

- **Shizuku**（推荐）：无需 Root，通过 ADB 授权即可
- **Root**：KernelSU / Magisk，直接以 shell 身份运行

### 每日实训的实现方式

**不做任务列表 OCR 识别，改为用户勾选。**

原因：崩铁每个号每天的实训任务是随机抽取的。早期尝试复刻 PC 版的「OCR 扫卡片 → 算分 → 补到 500」逻辑，但手游下极不可靠（OCR 拆字跨卡片、「宇宙」认成「字画」、卡片布局随文字长度浮动）。

现在的做法：用户在配置面板勾选今天要做哪几项，程序按顺序执行，每项做完回大厅确认，最后统一领奖。

## 🛠 源码运行与构建

### 环境要求

| 组件 | 版本 |
|---|---|
| JDK | 17+ |
| Android SDK | compileSdk **37** |
| **NDK** | **29.0.14206865**（必需，编译 `libbridge.so`） |
| CMake | 3.22.1 |
| 内存 | **建议 8 GB 可用**，低于此值 R8 易卡死 |

### 构建

```bash
# 1. 安装 NDK（必需）
sdkmanager --install "ndk;29.0.14206865"

# 2. 配置签名（可选，不配则 release 不签名）
# 在 local.properties 里写：
#   KEYSTORE_PATH=/path/to/your.jks
#   KEYSTORE_PASSWORD=***
#   KEY_ALIAS=***
#   KEY_PASSWORD=***

# 3. 构建
./gradlew :app:assembleDebug      # 调试版
./gradlew :app:assembleRelease    # 发布版
```

### R8 强度可配

在 `local.properties` 里设置：

```properties
# none  = 不混淆（开发调试，最快）
# light = 只混淆代码不压资源（开源发布，默认）
# full  = 全量混淆+资源压缩（上架商店，需 16GB 内存）
maa.r8=light
```

> ⚠️ **`libbridge.so` 的 JNI 类名不能被混淆**，`proguard-rules.pro` 里已用
> `-keep class ... { *; }` 锁定。改成 `{ native <methods>; }` 会导致
> `UnsatisfiedLinkError: JNI_ERR returned from JNI_OnLoad`。

## 任务包开发者

底部导航中间的「任务包开发」（也可从「设置 → 数据 → 任务包开发者」进入）是面向任务包作者的独立工具页。
它只增强开发过程，**导出的仍是原项目可导入的 `.m7atask`**：`schemaVersion: 1`、原有 24 种动作、根目录 `task.json` 与 `assets/`，没有新增执行接口或清单字段。

| 能力 | 说明 |
|---|---|
| 入口与横屏 | 底部导航中间的「任务包开发」直达全屏开发者页（原「定时」Tab 已替换）；进入自动切到传感器横屏，返回主界面恢复竖屏 |
| 画面布局 | **默认「专注画面」**：1920×1080 画面严格 16:9 居中，**全面屏左右两侧多出来的黑边正好用来放功能栏**——左侧竖排功能 Tab 与录制模式，右侧竖排工具条、控制与提示，画面完全不被遮挡、也不非等比拉伸。虚拟屏恒为 **1920×1080 / dpi 240**（不再跟随真机物理分辨率，避免游戏在两套分辨率间反复 restart、dpi 跳变导致画面异常），`SurfaceView` 缓冲同尺寸、等比居中投帧；侧栏宽度按可用高度算出 16:9 画面宽后取剩余黑边的一半（16:9 屏保底 92dp，画面等比缩小仍严格 16:9）。切到编辑类 Tab 自动回到左右分栏（左画面 / 右工作区 0.58:0.42）以容纳步骤树、AI 与模板内容，顶栏「专注画面 / 分栏编辑」可随时手动切换；「真全屏」则隐藏顶栏与两侧栏、只留 16:9 纯画面（右上角 X 退出）。工具条可切「等比完整」（内接、完整画面）与「等比铺满」（放大填满、裁边），**两种都恒等比例**；坐标仍归一化到 0～1，不影响任务包格式与执行器 |

| AI 读规范 | 生成时把《任务文件开发规范》（`docs/task-file.md`）**全文**作为独立 system 消息注入对话——模型无法自己打开 URL，必须由 App 读取正文，才能避免生成不符合规范的包。App 内置规范全文（离线可用、默认生效），AI 页可**添加/编辑/删除多个规范链接**，点「从链接读取规范」拉取线上最新版（GitHub `blob` 自动转 `raw`），任一失败自动回退内置全文；生成前取缓存、不联网，附带规范字数与来源可在界面查看，也可用开关完全关闭 |
| 校验导出 | 导出前复用原项目 `CustomTaskPackValidator`，可导出 `.m7atask` 或安装到本机试跑 |

**点击取词为什么之前识别不到**：原 `OcrEngine.detect()` 会把最长边超过 960px 的帧整体缩小到 960，
横屏 2400×1080 被压成 960×432，按钮小字直接丢失。开发者版不改原引擎（避免影响原项目执行器），
改为按点击点裁 900×600 主 ROI、560×380 紧邻 ROI 触发放大识别，再以全帧低阈值回退取最近文本框；
给 AI 的全屏 OCR 则按 ≤960px 分块识别，避免整帧缩放。AI 页「OCR 自检」可打印帧尺寸、
整帧/分块识别条数，便于现场排查。

**AI 不主动索取就不发图**：默认请求是纯文字的，普通文本模型也能用；只有模型判断文字不足以理解界面
并主动索取时，才抓取当前帧以 `image_url` 回填。端点不支持多模态或截图失败会自动降级为纯 OCR 文字继续，
不会让整轮生成失败。截图仅供理解界面，坐标与模板仍必须来自用户录制或明确提供。

版本填写 `x.x-y.y`：前段是任务包版本，后段是崩铁游戏版本，用短横线连接，例如 `1.2-4.7`。
「包版本」栏可以直接粘贴整串 `1.2-4.7`，工具会自动拆成两栏，**不会**再补一个短横线变成 `1.2-4.7-4.7`。
如果版本本来就不是这种格式（例如 `1.0.0`，或暂时没有对应游戏版本），只填「包版本」那一栏即可，
「游戏版本」留空，最终 `version` 就是 `1.0.0`，不会出现尾部短横线。
旧包里 `1.2.4.7` 这种四点写法导入时仍会自动解析成同样的两段。
开发者版**不会自行编造写进任务包的坐标或图标**：包内坐标来自用户实时操作或明确提供，模板来自用户框选或从模板库挑选的仓库真实素材；
AI 没有可靠坐标时只允许使用原版已有的 `tapText` / `waitText` 等文字动作。
AI 生成期的自动点击坐标只是推进界面用的探索行为，不写入包；模板库里的整包模板是仓库原文件
（其坐标与模板图由原作者提供），436 个图标模板全部是仓库/整包里已有的 PNG，工具不生成任何图像；
24 个步骤模板的坐标 / 模板 / 文字字段一律留空，由开发者在画面上取点后填写。

### 独立安装包名与 Shizuku 授权

开发者版使用独立 `applicationId`（`com.march7th.hkrpg.taskpack`），可与原项目共存，
桌面名称显示为「任务包开发者」。实时录制依赖 Shizuku 提供截图与触摸注入：

1. 首次安装、更换包名或更换签名后，Shizuku 会把它当作**新应用**。打开工具页「环境」标签，
   首次进入会自动发起一次授权请求，在 Shizuku 弹窗中允许即可；也可用「重新申请权限」「打开 Shizuku」「复制包名」自助操作。
2. 「环境」标签会显示**本包实际包名**（应为 `com.march7th.hkrpg.taskpack`）、`API_V23` 权限声明、
   Shizuku 版本、运行 UID、服务连接与授权状态，并按「未连接 / 已连接未授权 / 已授权」三种状态给出对应步骤。

> **为什么新包名会「识别不到 Shizuku」**：Shizuku 服务端并不是扫描全部已安装应用，
> 而是在应用进程**首次变为活跃**时，才检查它是否声明了 `moe.shizuku.manager.permission.API_V23`
> 并向 `<包名>.shizuku` 投递 binder，且每个 UID 只投递一次。因此「应用管理」列表只登记已投递过的应用。
> 换包名后若首次投递没发生，本应用就既不在授权列表里，也发不出权限请求。
>
> 遇到「环境」页显示 **未连接（binder 未送达）** 时，按此顺序处理：
> ① 确认 Shizuku 首页显示「正在运行」（adb / 无线调试启动的每次开机要重新启动）；
> ② **完全退出本应用或「强制停止」后重新打开**，让 Shizuku 重新投递并登记；
> ③ 仍不行则在 Shizuku 中**停止服务并重新启动**，再重开本应用；
> ④ 变为「已连接」后点「重新申请权限」并在弹窗中允许。
>
> 另外，权限申请会先等待 binder 就绪，不会因冷启动瞬间未连接而静默失败；
> 授权结果以 Shizuku 回调为准，不再因状态刷新滞后而误报失败。

## 🤝 参与开发

想新增任务或修改识别逻辑？请先阅读 [任务开发规范](docs/TASK_DEVELOPMENT.md)。

### 快速规范摘要

1. **优先区域识别**，不要全屏扫（性能差 5~20 倍）
2. **能用模板匹配就别用 OCR**，OCR 有拆字/误识风险
3. **按钮位置固定时直接写坐标**，比识别更可靠
4. **不要按 BACK**：游戏内 BACK 只会弹出「是否退出游戏」，没有返回上一级的作用；只点界面自带的 ✕ / 取消
5. **每个动作后确认界面状态**，不要连续盲操作
6. **兜底点击只用安全空白位**，绝不碰返回键、头像、右侧功能列、底部主按钮
